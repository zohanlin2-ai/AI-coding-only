# C Player 測試與驗證指南 (Testing & QA Guide)

影音播放器是一個高度依賴多執行緒同步與即時渲染的系統。本指南旨在說明如何對播放器進行全方位的品質驗證。

---

## 1. 自動化測試可行性評估 (Testability)

播放器的測試可分為「核心邏輯」與「視覺感知」兩大部分：

### 1.1 可自動化 (Highly Testable)
*   **數據結構 (Data Structures)**: 如 `PacketQueue`。可透過壓力測試模擬多執行緒競爭，確保 thread-safety 並無死鎖 (Deadlock)。
*   **解碼隔離測試 (Decoder Integration)**: 提供一個已知的檔案位元流，驗證解碼器是否能產出對應的 `AVFrame` 尺寸與像素格式。
*   **同步算法 (Sync Formulas)**: 模擬 Audio Clock 的變動，測試 Video Sync 邏輯計算出的 `delay` 補償值是否符合數學預期。

### 1.2 建議手動驗證 (Manual Testing Required)
*   **流暢度 (Smoothness)**: 影音是否掉幀 (Frame Drop) 或卡頓。
*   **音畫同步感 (A/V Perception)**: 雖然有數據指標，但人耳對聲音領先或落後的最終感受仍需人工確認。
*   **軟硬體相容性**: 不同顯卡驅動與音效裝置的渲染表現。

---

## 2. 手動測試清單 (QA Checklist)

在每次發布重大更新 (Main Release) 前，建議執行以下測試案例：

| 類別 | 測試項目 | 預期結果 |
| :--- | :--- | :--- |
| **基本播放** | 播放 MP4/H.264 檔案 | 畫面顯示正常，聲音清晰無雜音 |
| **播放控制** | 暫停 (Pause) / 恢復 (Resume) | 恢復播放後，影音應立即重啟且不失步 |
| **跳轉控制** | 捲動進度條 (Seeking) | 畫面能快速更新至目標時間，音畫同步應在 1s 內回復 |
| **異常邊界** | 開啟損毀或不支援的檔案 | 程式應優雅報錯，不應發生崩潰 (Crash) |
| **效能壓力** | 4K / 60FPS 影片播放 | CPU/GPU 佔用率穩定，不應持續攀升 |
| **資源管理** | 關閉程式 (Cleanup) | 所有解碼執行緒正確退出，無記憶體殘留或殭屍進程 |

---

## 3. 自動化單元測試實施建議

如果您未來計畫引入自動化測試，建議優先實作以下目標：

### 3.1 PacketQueue 安全測試
撰寫一個獨立程式編譯 `packet_queue.c`：
*   **測試 A**: 啟動 4 個寫入執行緒與 4 個讀取執行緒，驗證原子計數 (`nb_packets`) 是否始終正確。
*   **測試 B**: 在 Queue 滿載時測試 `SDL_cond_wait` 是否正確阻塞與喚醒。

### 3.2 同步邏輯 Mock 測試
建立一個類比時鐘：
*   模擬 Audio Clock = 10.0s, Video Clock = 9.8s。
*   呼叫同步函數，驗證其是否正確判定「Video 慢了」並縮短等待時間。

---

## 4. 效能與穩定性監控

建議在測試時開啟工具檢測：
1.  **Memory Leak**: 推薦在 Linux/macOS 使用 `valgrind`，Windows 可使用 `Dr. Memory` 或 IDE 自帶的分析工具。
2.  **CPU Profiling**: 觀察 `avcodec_receive_frame` 的佔用，確保解碼效率。

---

## 總結
雖然影音播放器難以達到 100% 的自動化覆蓋，但透過 **「邏輯層自動化」+「呈現層清單化」** 的雙軌機制，可以最大程度確保播放器的穩定性。
